# Meshing / Rigging / Relighting Gaussian Splats — Standard or Bespoke? (verified through 2026-08-09)

## 1. THE VERDICT

Everything is bespoke; nothing is a standard; the three capabilities differ in *how* bespoke. **Mesh extraction** is a *de-facto convention, not a format*: the ecosystem converged on one recipe (render per-view depth from regularized splats → Open3D TSDF fusion → marching cubes → vertex-colored PLY), re-implemented per-repo with Open3D as the only shared component — there is no spec, no working group, no ratification track, and the output discards all splat↔mesh provenance. **Rig/animation binding** is *converging conceptually but fully bespoke in serialization*: the research family (SuGaR-refined/Frosting/GaMeS/Mani-GS/SplattingAvatar/GaussianAvatars) all settled on the same parameterization — each Gaussian pinned to a parent triangle by barycentric-style coordinates + surface offset, mesh drives splats — but every implementation invents its own storage; KHR_gaussian_splatting (RC, verified 2026-08-09) is completely silent on skinning/JOINTS/WEIGHTS/morphs and even restricts node transforms to near-rigid decomposable TRS, so the *only* standards-backed splat motion today is rigid whole-primitive node animation, and the only animated-splat data that travels between tools is baked per-frame PLY sequences. **Relight-ready normals** is the most bespoke of the three: no convention exists that more than one tool both reads AND writes — PLY nx/ny/nz is conventionally all-zero (Inria trainer writes zeros, SuperSplat strips them; only V-Ray documents reading them if present, DECLARED), KHR and SPZ define no normal/material semantics in any version, and every relightable-GS research pipeline invents per-splat storage under Inria non-commercial licenses. There is no "open standard for meshing gsplats" to support — not ratified, not RC, not even formally proposed.

## 3. THE STANDARDS LANDSCAPE

- **Khronos**: KHR_gaussian_splatting is the only splat spec on a ratification track, still **Release Candidate** as of 2026-08-09 (ratification was "expected Q2 2026" — it has slipped; repo text is authoritative). It is static-only by construction. Origin issue #2454 raised animation exactly once (2025-06-04, three passing comments, dismissed — "no support for morphing/animation is pretty OK"); **zero** mentions of skinning, 4D splats, or per-splat normals anywhere in the Khronos pipeline, even at discussion stage. The spec explicitly sanctions layered extensions ("Extensions MAY define additional attributes… alternative lighting methods") — that mechanism is the *designated* future home for binding/normal semantics, but the home is empty.
- **SPZ (Niantic)**: format authority for compression, MIT, no normals ever; v4's vendor-extension records (plaintext-zone ILV, no global registry) are a shipping-today vehicle a vendor could use for normals — nobody has.
- **USD/AOUSD**: the *most-ratified* splat representation anywhere (shipped in core OpenUSD v26.03), but static, and not our format lane.
- **MPEG-I GSC**: exploration stage under Part 45; the **only** standards body explicitly targeting dynamic/time-varying splats (test-material call due 2026-10-15) — and it is ISO/RAND patent territory, not Khronos royalty-free.
- **MSF**: coordination-only town halls (Cozzi/Medvedev); no normative output; the glTF↔USD alignment venue.
- **Closest thing to "an open standard for meshing gsplats"**: there is none at any formality level. The nearest artifacts are (a) the TSDF recipe — a convention with literal shared parameter defaults but no spec, no name, no body; and (b) the binding family's barycentric parameterization — a convention with no serialization. Distance from real: no draft exists, no WG has claimed the space, and the one body that could (Khronos, where Cesium sits) has never discussed it. Expect first movement as a KHR sibling extension or SPZ vendor extension, not a new standard.

## 4. RECOMMENDATION

- **Support-now: nothing new.** The only ratified-adjacent capability in our format lane is what we already have: KHR_gaussian_splatting (RC) static splats + **rigid node-TRS animation of whole splat primitives**, which composes implicitly with the glTF animation machinery the fork already ships. One cheap, probe-verifiable candidate row for the C15-G lane: verify our KHR_gaussian_splatting path actually applies animated node transforms to splat means per the spec's "effective global mean vector" clause (acceptance: animated-node splat primitive renders with motion, WebGL/WebGPU parity probe) — that is spec-conformance work, not new invention. Also **correct the fork's recorded license note**: the extension spec is Khronos Spec Copyright, not CC-BY.
- **Pre-register-and-watch** (name these as watch rows, no implementation; suggest attaching to the C18 Wave S seed / §6d ruling context rather than the live C15-G queue):
  1. Trigger: **KHR_gaussian_splatting reaches Ratified** → re-audit our loader against final text.
  2. Trigger: **any KHR sibling/vendor extension defining splat skinning, mesh-binding, or NORMAL/material attribute semantics appears** (watch KhronosGroup/glTF PRs + issue #2454) → this is the "open standard for meshing/rigging gsplats" the maintainer asked about, and today it does not exist even as a draft.
  3. Trigger: **PR #2531 merges** → update the vetted SPZ loader path; note the v2-pin vs v2/v3/v4 generalization outcome.
  4. Trigger: **an SPZ vendor extension or shipping tool starts writing real normals** (incl. nonzero PLY nx/ny/nz from any mainstream trainer) → revisit relight ingest.
  5. Trigger: **MPEG-I GSC issues a CfP** → assess with the explicit flag that it is RAND, not royalty-free.
- **Build-nothing-yet**: in-engine mesh extraction (offline authoring concern; entire research stack is Inria non-commercial = STUDY-ONLY; a clean-room path exists via papers + Apache-2.0 gsplat + MIT Open3D if a product need ever appears), splat skinning (bespoke everywhere; if ever built, Spark's MIT covariance-skinning is the study reference and the *strategic* move is proposing joints/weights or barycentric-binding accessor semantics through Cesium's WG seat, not shipping a fork-only format), and per-splat normal/albedo storage (no standard slot; near-term relighting, if wanted, is derivable normals + baked-color-as-albedo + lighting-blend in WGSL — zero format changes). Any of these becoming a real row requires probe-verifiable acceptance criteria per fork policy.
- **Hard constraint restated**: every research repo in the meshing/binding/relighting families that mattered was verified or flagged Inria/MPII non-commercial lineage — all STUDY-ONLY for this Apache-2.0 fork. Clean-license islands: gsplat (Apache-2.0), Spark (MIT), gaussian-vrm (MIT), SPZ (MIT), Open3D (MIT), GauStudio (MIT-declared *except* rasterizer — unreviewed carve-out).
