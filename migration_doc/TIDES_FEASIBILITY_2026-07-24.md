# TIDES FEASIBILITY REPORT — CesiumJS WebGPU fork (2026-07-24)

## 1. Direct answer to the maintainer hypothesis

**The mental model of the default path is correct. The conclusion "probably nothing is possible" is refuted — by the fork's own code and design docs.**

What holds, precisely:

- **The imagery-visible ocean IS a solid tiled terrain mesh, same as land.** The water mask changes fragment shading only, never geometry: `GlobeFS.glsl:53-54, 485-490` (WebGL) and `packages/engine/Source/Shaders/WebGPU/Globe/GlobeTerrain.wgsl:432-433, 3846, 2291-2458` (WebGPU) sample the mask in the fragment stage; the fork's own ledger states "zero ocean-surface geometry existed before" the FFT ocean (`migration_doc/DEFERRED_WORK.md:5252`). Nothing moves the baked sea for free.
- **The WMTS intuition is right as far as it goes**: NOAA nowCOAST-class WMS/WMTS water feeds are pre-symbolized 2D raster imagery — appearance only, no height field, cannot drive geometry. No WMTS/WMS product anywhere delivers tide height as consumable geometry.
- **The 3D-tileset intuition is right about the product landscape**: no separated ocean-surface 3D Tiles asset exists anywhere (Cesium ion catalog, third parties — two independent search sweeps, negative). That half of the split is always application code.

What the hypothesis missed — four things, all already in or near the tree:

1. **The fork already ships a real 3D ocean surface** (C6-FFT-OCEAN, Batch 654, opt-in `scene.globe.water.ocean.enabled`, default off): a camera-anchored ENU patch FFT-displaced by compute, drawn over the terrain. Its sea level is assembled in backend-agnostic JS each frame at ellipsoid height 0 (`Scene/OceanSurfacePrimitive.js:115-167`, "height 0 datum"). A tide offset along the already-computed `_a0Up` is an incremental change to an existing feature, not a new architecture.
2. **The fork's own design doc already reserves the hook**: `scene.globe.water.tideCallback // (positionWC, time) => meters; null → 0` (`migration_doc/WATER_RENDERING_DESIGN.md:675`, ruling OQ5 at `:798` — "User-provided callback, default zero. Leave room to expand the default later"). Offset injection is in-scope by the project's own record; only in-engine tide *computation* is the declared non-goal (`migration_doc/FEATURE_INVENTORY.md:1119`).
3. **Per-frame vertex-stage vertical displacement already exists on both backends** (verticalExaggeration): `GlobeVS.glsl:245-258` and `GlobeTerrain.wgsl:1234-1284` displace terrain vertices along the geodetic normal with no re-tessellation, with working invalidation machinery (`Scene/GlobeSurfaceTileProvider.js:402-416`). A water-mask-gated tide offset is the same mechanical pattern; the mask is one visibility flag away from the vertex stage on WebGPU (`Renderer/WebGPU/WebGPUGlobeSurfaceLayouts.ts:148-149`, FRAGMENT → VERTEX_FRAGMENT) and WebGL2 guarantees vertex texture fetch.
4. **The bathymetry-plus-ocean split you proposed is already half-shipped**: `Core/createWorldBathymetryAsync.js:38-44` (Cesium World Bathymetry, ion asset 2426648, merged land+seafloor terrain), runtime terrain-provider swap with full tile invalidation (`Scene/Globe.js:703-711`, `Scene/GlobeSurfaceTileProvider.js:268-278`), and the FFT primitive as the ocean layer. No WMTS feed or land/ocean-separating 3D tileset is required — CesiumJS has exactly one terrain provider per Globe, so the separated architecture is necessarily (bathymetric terrain) + (app-drawn water surface), and both halves exist in-tree.

On the data side the hypothesis's framing (tide data must arrive as tiles) also fails: a global tide field is analytically compact. EOT20 (CC BY 4.0, confirmed verbatim) bakes to a ~2–8 MB constituent texture evaluable for ~8 fetches + 16 MADs per sample, and a zero-data equilibrium tide is computable from the engine's own Simon-1994 sun/moon (`Scene/FrameState.js:381/389/397`, `Core/Simon1994PlanetaryPositions.js:638/670`).

**False-hope guard (equally important):** real tide signal is ±0.3 m (equilibrium) to 1–16 m (resonant coasts) on a 6,371 km sphere — sub-pixel at globe distances. Visible tides need shoreline framing or a disclosed exaggeration knob. Nothing here is nearshore-accurate hydrodynamics. The fork has **zero existing tide hooks** (case-insensitive grep confirmed: only `mulTIDEck`/`IdenTIty`/`WebTide` false positives). And the single biggest correctness risk is **UNCONFIRMED: the vertical datum of the Cesium World Terrain ocean lid** (ellipsoid 0 vs geoid, ±~100 m regionally) — probe before building anything vertical.

## 2. What the fork can do, ranked by value-per-effort

**Rank 1 — Design A: tide-height offset on the FFT ocean (S–M, 1–2 batches).** Compute `tideHeight(t, lat, lon)` in JS (equilibrium term from Simon-1994, ~100 LOC of published math; later swap in EOT20 samples) and offset the patch anchor along `_a0Up` in `OceanSurfacePrimitive.update()` (`OceanSurfacePrimitive.js:152-156`). Zero WGSL change needed — the RTE EncodedCartesian3 split absorbs the offset; if a per-vertex term is ever needed, `OceanUniforms` has two zero pad slots (`WebGPUOceanRenderer.ts:925,929` ↔ `OceanSurface.wgsl:24,26`), so no new ShaderDefine bit and no C11-149 define-width prerequisite. Both-backends cost: **none new** — the offset is backend-agnostic scene JS on an already-ratified WebGPU-only primitive (WebGL no-op documented, `Scene/GlobeWaterOcean.js:9-14`); the deferred WebGL2 FFT fallback would inherit it automatically. Licence: none (published physics) or EOT20 CC BY.
Honest limits: (a) equilibrium amplitude is ~±0.2–0.3 m — qualitatively right (12.42 h period, spring/neap, diurnal inequality emerge from real geometry) but 2–10x too small and phase-wrong at coasts (amphidromes); needs a documented `tideExaggeration` knob and a "stylized, not a prediction" label. (b) Datum: patch anchors at ellipsoid 0; CWT's sea may sit at the geoid (UNCONFIRMED — probe). (c) Tide-down: the opaque baked sea mesh occludes the patch below it; within A the patch is biased up by max amplitude and the cycle reads as waterline motion on the coast slope, with the exposed strip showing baked water imagery, not seabed. (d) Coverage: 3 km patch, low altitude only, until the already-tracked C6-FFT-OCEAN-CLIPMAP lands (`DEFERRED_WORK.md:5252`).

**Rank 2 — Design D: appearance-only (S, possibly zero engine change).** Tide-phase intertidal styling via the already-ported ElevationRamp/Band/Contour globe materials (`GlobeTerrain.wgsl:668-678`, both backends) restyled by an app-side clock; and/or time-dynamic WMTS flood-extent overlays (`Scene/TimeDynamicImagery.js` + WebMapTileServiceImageryProvider, upstream, both backends). Buys flood-extent painting and a wet-strip cue on the up half-cycle only; cannot show tide-down; nothing moves in 3D. Ship as a "Tide Inspector" Sandcastle demo (Weather Inspector precedent) that doubles as the app-side `tideCallback` driver for A.

**Rank 3 — Design B: water-mask vertex displacement of the terrain mesh (M–L, 2–4 batches + prerequisites).** The only cheap design where tide-DOWN visibly lowers the ocean on stock CWT. Mechanics proven: reuse the exaggeration displacement path (`GlobeTerrain.wgsl:1258-1284` shared `processVertex`, all 6 entry points; `GlobeVS.glsl:246-248` twin) modulated by a VS water-mask sample. New plumbing: WebGPU bind-group VERTEX visibility (`WebGPUGlobeSurfaceLayouts.ts:148-149`), WebGL GlobeVS vertex texture fetch, ancestor-mask translation/scale replication (`GlobeTerrain.wgsl:327`), skirts and CV/2D/morph legs must take the same offset. Honest artifact bill: coastline smear (65×65 grid vs 256×256 mask → 1–2-texel stretch band, plus stretched water-colored imagery in the exposed strip), T-junction risk with ancestor masks, lakes/rivers share the mask (an alpine lake displaced −2 m grows a rim trench unless gated to raw height ≈ sea level), and renderer-vs-CPU divergence (pick/depth/shadows see displaced water; sampleTerrain/clampToGround/camera collision do not). Sequencing: same shader region as C11-158/C11-172; any define-gated form lands after C11-149 (define-width HARD PREREQ; registry bits 0–30 full).

**Rank 4 by cost, rank 1 by correctness — Design C: bathymetry terrain + planetary ocean shell (XL epic, own campaign).** Exactly the maintainer's instinct, and the only design where tide-down exposes real seabed. Pieces: (a) bathymetry — ion asset 2426648 streams today via `createWorldBathymetryAsync` (stream-only, see licence table) or self-hosted GEBCO tiles (public domain; requires a quantized-mesh tiling pipeline — real tooling work; upstream cesium-terrain-builder outputs heightmaps only, quantized-mesh lives in the ahuarte47 fork branch and coronis-computing/emodnet_qmgc); (b) water layer — the FFT patch scaled via C6-FFT-OCEAN-CLIPMAP plus the geoid+tide datum from A; (c) depth-composited translucency (Beer-Lambert seabed-through-water) — scaffolding partially exists (refraction target in WebGPUSceneFramebuffer, C6-SCREEN-SPACE-REFRACT designed, C6-PLANAR-REFLECT-REFRACT decomposed and unblocked-but-deferred, `DEFERRED_WORK.md:5254-5256`). Multi-week, 3–4 phases. Note: under bathymetric terrain the CWT water-mask semantics do not carry over (UNCONFIRMED whether CWB serves a mask at all) — the fork draws the ocean surface regardless, which is the point.

**Design E (variant, note only):** B's plumbing used once, statically — displace masked terrain down by a constant ≥ max tide range so A's surface is the only visible sea; both tide directions on stock CWT with a synthetic shallow seabed strip (baked-water-imagery texture — honest artifact). B's preferred end-state if B is ever built; not cheaper than A alone.

**Data tiers for A (and later C):** Tier 0 = equilibrium from in-engine ephemeris (zero data, zero licence; note `Moon.update` is the writer of `moonDirectionWC` — a tide consumer must require the moon enabled or call Simon1994 directly). Tier 1 = bundled EOT20 8-constituent texture (M2,S2,N2,K2,K1,O1,P1,Q1), Re/Im encoding so bilinear filtering never crosses a phase wrap; ~2–8 MB VRAM at 0.5–1.0 deg; offline bake script in Tools/ (pyTMD, MIT, as clean-room reference); the 2 GB source never ships. Runtime: per frame 8 sin/cos on CPU + 2 uniforms per constituent; per sample 8 rg16 fetches + ~16 MADs — not a compute problem. Tier 2 = NOAA CO-OPS per-station overlay for US close-ups (runtime API, nothing bundled).
