## Lane summary

MESH-EXTRACTION-FROM-GSPLATS LANE (through mid-2026). CONVERGENCE ANSWER: no single named tool won; the field converged on a RECIPE — rasterize per-view depth from surface-regularized splats, TSDF-fuse in Open3D, marching-cubes to a vertex-colored PLY — re-implemented per-repo by 2DGS (the baseline representation), RaDe-GS, PGSR, and GS2Mesh, with GOF's marching-tetrahedra-on-opacity-field as the adaptive alternative and SuGaR's Poisson path as the 2024 original. The 2025 successor direction is MILo (SIGGRAPH Asia 2025, same Inria group as SuGaR): differentiable mesh extraction inside the training loop, ~10x fewer vertices — meshing is moving upstream into splat authoring, not staying a post-hoc converter. OUTPUT FORMATS: research pipelines emit PLY only (vertex colors, no UVs); SuGaR uniquely emits textured OBJ; the only glTF-out pipeline is the commercial KIRI Engine 3DGS-to-Mesh 3.0 (OBJ/FBX/glTF with baked UV textures; its core open-sourced as GauStudio, DECLARED MIT-except-rasterizer — the license-cleanest meshing code found). BINDING ANSWER: pure meshing pipelines all DISCARD the splats; a separate, well-converged family (SuGaR-refined hybrid, Frosting, GaMeS, Mani-GS, SplattingAvatar, GaussianAvatars) preserves splat<->mesh correspondence via a de-facto-standard parameterization — each Gaussian pinned to a parent triangle by barycentric coordinates + normal offset, so mesh rigging/bones drive the splats — but serialization is bespoke per-repo and the KHR_gaussian_splatting RC has no mesh-binding slot (a standards vacuum that composes naturally with the fork's glTF skinning stack if it ever wants rigged splats). LICENSE MINEFIELD (files fetched literally where it mattered): SuGaR and GOF are CONFIRMED Inria/MPII non-commercial at LICENSE.md; RaDe-GS is CONFIRMED research-only (custom HKUST terms); MILo DECLARES partial Gaussian-Splatting-License coverage and runs only on RaDe-GS/GOF backends; 2DGS-reference, PGSR, and GS2Mesh all declare Inria-3DGS lineage (exact terms unfetched — treat as non-commercial). Essentially the ENTIRE research meshing stack is unshippable in an Apache-2.0 fork. Clean paths: re-derive algorithms from papers; gsplat's Apache-2.0 reimplementation of 2DGS rasterization (mesh extraction itself still 'planned', not shipped); GauStudio's MIT-declared layers pending rasterizer-carve-out review; Open3D TSDF (MIT). - **TSDF-fusion-of-rendered-depth (the converged meshing recipe: render per-view depth from splats -> Open3D TSDF fusion -> marching cubes -> PLY)** [DE-FACTO-CONVENTION, Established 2024, still the default in 2025-2026 papers; every repo re-implements it rather than sharing a library (Open3D is the only shared component).] - The one process the ecosystem actually converged on is not a tool but a recipe: rasterize depth maps of the training views from the (regularized) splats, fuse them with Open3D's ScalableTSDFVolume (typical params voxel_size~0.004, trunc~0.02), run marching cubes, emit a vertex-colored PLY. 2DGS shipped it with bounded + unbounded (space-contraction) modes; RaDe-GS, PGSR, GS2Mesh, and GOF's fallback path all reuse the same shape. The splats are DISCARDED after fusion — no splat-to-triangle provenance survives in any TSDF pipeline. Output is always PLY (vertex colors, no UV textures); nobody in the research stack emits glTF or OBJ from this path except SuGaR. License: The recipe itself is unencumbered; Open3D is MIT (DECLARED, Open3D repo). Each implementation carries its own repo's license — usually Inria-lineage non-commercial (see per-method findings). Fork: If the fork ever offers splat->mesh conversion (collision meshes, occlusion proxies, 3D-printable export from its 3D Tiles gsplats), this recipe can be re-implemented cleanly from the paper descriptions + Open3D/own WGSL compute without touching any Inria-licensed code — depth rasterization of splats is something the fork's renderer already half-does. Expect PLY-style vertex-colored output, not textured glTF, unless a texturing pass is added.

Critically, its refinement stage produces a hybrid representation with Gaussians BOUND to the mesh surface and jointly optimized — an explicit splat-to-triangle binding that survives, with a Blender add-on (sugar_frosting_blender_addon) to edit/animate the mesh with splats riding along. - **MILo (Mesh-In-the-Loop Gaussian Splatting)** [RESEARCH, SIGGRAPH Asia 2025; the freshest major entry in this lane and the likely successor-of-record to SuGaR/2DGS for quality-per-vertex; repo active 2025-2026.] - SIGGRAPH Asia 2025 / TOG 44(4) (Guedon, Gomez, Maruani, Gong, Drettakis, Ovsjanikov — Inria/Ecole Polytechnique). - **Spark 2.0 (World Labs) — skinned splats in three.js (dual-quat + experimental LBS)** [TOOL, Shipping, actively developed (2.0 released 2026); LBS path explicitly labeled experimental. WebGL2/three.js, runs desktop/mobile/WebXR.] - The most engine-real web implementation of runtime splat skinning. Spark 0.1 shipped dual-quaternion blending for skinned splats with binding represented as 'B deformable bones and N x 4 bone indices and weights per splat' (docs quote). Spark 2.0 (2026) adds an optional covariance-splat representation (stores the 3D symmetric covariance matrix instead of scale+rotation, enabling non-uniform/affine transforms) and on top of it EXPERIMENTAL Linear Blend Skinning, explicitly 'opening the door to animating splat characters using existing mesh-based rigging systems'. Loads PLY/compressed PLY, SPZ, SPLAT, KSPLAT, SOG; also has a .RAD streaming format. Binding representation: per-splat bone indices+weights supplied through the Spark/three.js API — no serialized interchange format and no glTF-skin wiring documented. License: MIT (declared, GitHub sidebar of sparkjsdev/spark) Fork: HIGH as reference implementation: per-splat (indices4, weights4) + LBS-on-covariance is exactly the shape a WGSL compute prepass would take in this fork, and the covariance-splat trick (skin the covariance matrix, not scale+rot quaternion) is the key numerical design decision to copy. MIT means code can be read and derived from with attribution. Not portable as data — API-level binding only.
- **gaussian-vrm / 'Instant Skinned Gaussian Avatars' (.gvrm) — splats + glTF-based VRM skeleton** [RESEARCH, Published Oct 2025, working cross-platform demos (web/mobile/VR), research-grade code with releases.] - The closest existing thing to 'splats skinned to a glTF skeleton'. Three.js system (built on three-vrm + gaussian-splats-3d) where splats dynamically follow the vertices of a skinned VRM mesh (VRM = glTF-based humanoid avatar format) via parallel splat-wise processing; smartphone scan to animated avatar in ~5 min; 40-50 fps on iPhone 13 Pro, 240 fps on RTX 3060 laptop. Defines a bespoke .gvrm container combining the splat cloud with the VRM/glTF skeleton+mesh. Binding representation: splats follow mesh vertices (mesh-driven, not direct per-splat bone weights); the rig itself IS a glTF/VRM skeleton, but the splat-to-mesh binding lives in the .gvrm container, not in a glTF extension. Authors: Kondo, Asano, Ochiai; SUI 2025 demo. Notably avoids SMPL and restrictively-licensed models on purpose. License: MIT for code (declared in README, explicitly chosen to avoid SMPL-style restrictions); sample assets research-only/separately licensed. Paper CC-BY 4.0. Fork: HIGH. Proves the two-layer pattern the fork could standardize: glTF skeleton + skinned proxy mesh drives splats bound to that mesh. A KHR-friendly path would serialize the splat-to-mesh binding as glTF attributes instead of a bespoke .gvrm. MIT license makes it minable.
- **GaMeS — barycentric triangle binding of flat gaussians (mesh-bound family root)** [RESEARCH, 2024 paper, heavily cited; the 'bind splats to triangles' idea is now the de-facto conceptual convention across DCC tools and research, but each implementation re-invents the serialization.] - Foundational mesh-binding paper (Waczynska et al., arXiv 2402.01459). Each gaussian is parameterized by the vertices of a mesh face: mean = convex/barycentric combination of the triangle's vertices (trainable weights summing to 1), rotation taken from the triangle's frame, gaussians constrained to flat ellipses lying on the surface, N splats per face. Deforming the mesh automatically re-poses position/scale/rotation of every bound splat — rigging/animation for free through any mesh deformer. Binding representation: (face id + barycentric weights + per-face frame) — implicit in the trained parameterization; no interchange format defined. Descendants: GS-Verse (VR physics interaction, 2025), MeshSplatting, Mesh2GS. License: Inria/MPII 'Gaussian-Splatting' NON-COMMERCIAL research license — CONFIRMED by fetching LICENSE.md literally: 'THE USER CANNOT USE, EXPLOIT OR DISTRIBUTE THE SOFTWARE FOR COMMERCIAL PURPOSES WITHOUT PRIOR AND EXPLICIT CONSENT OF LICENSORS.' Classic Inria-lineage trap: code is off-limits for this fork; the ALGORITHM (barycentric binding) as described in the CC-licensed paper is implementable clean-room. Fork: MEDIUM-HIGH. The binding SCHEME (triangleIndex + barycentric + normal-offset per splat) is trivially expressible as extra glTF attribute accessors on a splat primitive referencing a sibling mesh — the most portable candidate representation found in this survey. Do NOT derive from the repo code.
- **Mani-GS (CVPR 2025) — triangle binding with self-adaptation for large deformation** [RESEARCH, CVPR 2025 paper with released code and demo data.] - Gaussian Splatting Manipulation with Triangular Mesh (Gao et al.). Binds gaussians to an extracted triangle mesh via a binding strategy 'with self-adaption' using per-triangle local coordinate frames — unlike GaMeS it allows splats to deviate from the surface (local offset in the triangle frame), preserving quality under large deformation, stretch, and soft-body simulation (repo ships deform_stretch and softbody demo sequences driven by per-frame OBJ meshes). Binding representation: per-splat (triangle id + local-frame coordinates), again training-internal with no interchange format; animation is transferred by supplying deformed mesh sequences. License: UNKNOWN — no LICENSE file visible on the repo page I fetched; given it builds on 3DGS pipelines, assume Inria lineage until the repo is checked file-by-file. Fork: MEDIUM. The triangle-local-frame-with-offset refinement over pure barycentric binding is the version that survives real animation (skirts, muscles); any fork binding convention should adopt (triId, barycentric, normalOffset, localRot) rather than GaMeS's surface-locked form. License must be resolved before touching code.
- **SMPL-driven animatable Gaussian avatar family (GauHuman, GART, Animatable Gaussians + 2025 survey)** [RESEARCH, Very active 2024-2026; dozens of papers; converging on LBS-per-splat as the standard math but not on any format.] - The dominant academic skeleton-skinning line: gaussians live in a canonical space initialized from SMPL(-X) vertices and are warped to observation space by forward Linear Blend Skinning using per-splat blend weights, usually learned/MLP-refined (GauHuman: LBS refinement; GART: learnable blend skinning over articulated templates; Animatable+Relightable Gaussians). Surveyed comprehensively in Frontiers in AI 2025 'Human reconstruction using 3D Gaussian Splatting: a brief survey'. Binding representation: per-splat skinning weights against the SMPL skeleton — conceptually identical to glTF JOINTS/WEIGHTS but every codebase stores it bespoke (checkpoints/tensors), zero interchange. Newer work generalizes to arbitrary skeletons (G-Skin 2026, RigPAPR, SketchRodGS). License: Varies per repo and mostly UNTRUSTWORTHY for a commercial fork: double lineage flag — Inria 3DGS code ancestry (non-commercial) AND SMPL body-model licensing (research-free, commercial via Meshcapade). Verify per repo; treat as tainted by default. Fork: MEDIUM as math reference (per-splat LBS on mean + rotation, weight initialization from nearest proxy vertices), LOW as code source. Confirms per-splat (joints, weights) is the community-consensus representation a glTF skinning extension for splats should encode.
- **Cage/lattice deformation: GSDeformer + CAGE-GS** [RESEARCH, 2024-2025 papers with code (main code + separate cage-builder repo); real-time claimed and demonstrated.] - GSDeformer (arXiv 2405.15491): real-time cage-based deformation of vanilla 3DGS with no retraining — converts gaussians to a proxy point-cloud representation, applies cage deformation (generalized barycentric/mean-value coordinates) to the proxy, translates the result back into per-gaussian transforms, with a splitting step to approximate bending; automates cage construction; explicitly extensible to 3DGS variants. CAGE-GS (2025) is a higher-fidelity successor. Binding representation: cage vertices + per-splat cage coordinates — cages are a standard DCC concept (lattices) so the representation is conceptually portable, but neither paper defines a serialization. License: UNKNOWN — GSDeformer repo has a LICENSE file whose type was not visible in the fetched page; Inria-lineage risk unassessed. CAGE-GS license UNKNOWN. Fork: MEDIUM. Cage deformation is the no-training path to animating arbitrary CAPTURED splats (no rig, no proxy mesh extraction quality dependence) — relevant for animating scanned 3D Tiles splat content where no skeleton exists. Cage coords per splat would also serialize naturally as glTF attributes.
- **KIRI Engine 3DGS Render 5.0 (Blender add-on) — proxy-mesh binding + armature transfer** [TOOL, Shipping, v5.0.0 June 2026, actively developed, large user base via KIRI Engine.] - Free Blender add-on; v5.0 (June 2026) makes 3DGS scans animatable inside Blender by binding the splat object to a proxy mesh ('Bind to Proxy Mesh': splat object parented to the proxy, transforms locked), including RIGGED characters — animate the proxy with a standard armature and the animation transfers to the splats; also bakes lighting from proxy to splats.
