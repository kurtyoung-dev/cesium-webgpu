## 1. Executive summary

1. **Direction A — one renderer, one shader source, backends below the line.** three.js confines all divergence under an abstract `Backend` and compiles one TSL node graph to WGSL or GLSL ([THREE-A01](#three-a01)–[A04](#three-a04)); luma.gl assembles one unified WGSL with `@binding(auto)` and named injection hooks ([LUMA-A4](#luma-a4), [A5](#luma-a5)); MapLibre sequences UBO-first WebGL2 before a WebGPU backend behind one interface ([C17](#c17)).
2. **Direction B — GPU-driven everything.** Compute-built cluster light lists ([THREE-F01](#three-f01)), GPU hierarchy traversal with a screen-space-error metric feeding indirect draws ([LUMA-F2](#luma-f2)), GPU-native splat sorting and residency ([LUMA-F4](#luma-f4), [C23](#c23)), frame-graph pass ordering with graph-owned transients ([LUMA-A6](#luma-a6)), and a TSL software rasterizer ([C22](#c22)) — all without mesh shaders or multi-draw-indirect, which remain outside the web ([WGPU-18](#wgpu-18), [WGPU-19](#wgpu-19)).
3. **Direction C — a platform at Candidate Recommendation that grows by feature detection.** WebGPU and WGSL are CR Drafts ([WGPU-01](#wgpu-01), [WGPU-02](#wgpu-02)); immediates, compatibility mode, transient attachments, `primitive_index`, `linear_indexing`, subgroup size control, dual-source blending on Firefox, and a Dawn-prototyped bindless resource table all arrived since July ([WGPU-04](#wgpu-04)–[WGPU-17](#wgpu-17)); f64 is not coming ([WGPU-25](#wgpu-25)).
4. **Where the fork stands on A:** the `GraphicsContext` + `FeatureRenderer` shape is the same as three.js's and MapLibre's, and upstream still has no renderer abstraction to converge on ([C02](#c02)); but the fork keeps two live scene executors above the context boundary ([THREE-A01](#three-a01) row) and authors every shader twice ([THREE-A03](#three-a03), [C20](#c20)).
5. **Where the fork stands on B:** Forward+ clustered lighting already exceeds three.js r185 on capacity ([C21](#c21)); pipeline keys fold module identity as three.js and luma do ([THREE-A05](#three-a05), [LUMA-A3](#luma-a3)); but GPU traversal, scene-level indirect draw generation, GPU splat sort and a frame graph are all scaffold or absent ([LUMA-F1](#luma-f1), [F2](#luma-f2), [F4](#luma-f4), [A6](#luma-a6)).
6. **Where the fork stands on C:** the optional-feature list is negotiated per adapter, but no `ShaderDefine` bit is ever populated from `navigator.gpu.wgslLanguageFeatures`, so every new WGSL extension lands as a string-prepend outside the module cache ([WGPU-02](#wgpu-02) row); `primitive_index` is treated as core ([WGPU-03](#wgpu-03)); the transient-attachment gate can never match ([WGPU-08](#wgpu-08)); dual-source blending is requested but unwired ([WGPU-13](#wgpu-13)).
7. **The RTE rule is vindicated and now carries a new risk.** No platform f64 relief ([WGPU-25](#wgpu-25)); deck.gl's per-viewport rebase is weaker than the fork's per-vertex high/low split ([DECK-G1](#deck-g1)); but luma documents that the Metal compiler reassociates error-free transforms on Apple adapters ([LUMA-G3](#luma-g3)) and the fork has neither an integer-controlled `twoSum` nor an Apple probe lane.
8. **Upstream moved under the fork.** CesiumJS 1.145 (2026-09-01) rewrote `ClippingPolygons` with holes and draped vectors onto 3D Tiles ([C01](#c01), [C15](#c15)); the fork's WGSL SDF-atlas path has no hole concept and WebGPU polygon draping is absent even on terrain; the 1.146 edge-vertex-array leak is present in the fork's WebGL lane ([C13](#c13)).
9. **Ranked gap list (§4):** the 1.145 sync, Apple-adapter precision, extension-detected define bits, dual-source OIT, the snap gates, the voxel default shader, then the three XL structural items (GPU-driven traversal/draw generation, splat GPU path, frame graph) and the single-scene-executor consolidation.
10. **What not to copy (§5):** a TSL-style single-source rewrite, deck.gl's precision model, compatibility mode as a WebGL replacement, the TSL software rasterizer, `instance_index`-only picking, per-pass submits, and any bindless build on a Canary flag.

## 2. Per-target findings

### 2.1 three.js `WebGPURenderer` + TSL (mrdoob/three.js)

**Latest release:** r185, 2026-07-01 ([releases/r185](https://github.com/mrdoob/three.js/releases/tag/r185)). r186 is in `dev` (native splat renderer merged) but was not a GitHub release on 2026-09-02 ([C23](#c23), secondary source).
**What changed architecturally since the 2026-07-05 audit:** r183 renamed `PostProcessing` to `RenderPipeline` (node-graph post-processing with MRT and automatic pass fusion); r184 added `DynamicLighting`; r185 added `ClusteredLighting` (removing `TiledLighting`), restored WebXR on the WebGPU backend, introduced cached/reset descriptor classes, surfaced uncaptured GPU errors and WGSL diagnostics, and merged a TSL software rasterizer.

<a id="three-a01"></a>**THREE-A01** (CONFIRMED) — `WebGPURenderer` is one shared renderer over pluggable backends: WebGPU by default, silent fallback to a WebGL 2 backend, `forceWebGL` pins WebGL 2. Source: <https://threejs.org/docs/pages/WebGPURenderer.html> — "By default, the renderer tries to use a WebGPU backend if the browser supports WebGPU. If not, `WebGPURenderer` falls backs to a WebGL 2 backend."

<a id="three-a02"></a>**THREE-A02** (CONFIRMED) — All backend-specific behaviour is confined to an abstract `Backend` (beginRender/finishRender, draw, compute, createRenderPipeline, createBindings, getRenderCacheKey, createNodeBuilder, isOccluded, …); the common `Renderer` holds rendering logic. Source: <https://raw.githubusercontent.com/mrdoob/three.js/dev/src/renderers/common/Backend.js> — "This abstract base class defines an interface that encapsulates all backend-related logic. Derived classes for each backend must implement the interface."

<a id="three-a03"></a>**THREE-A03** (CONFIRMED) — Shaders are authored once as a TSL node graph and compiled by `WGSLNodeBuilder` or `GLSLNodeBuilder`; no dual hand-written source, no textual preprocessor/defines layer. Source: <https://github.com/mrdoob/three.js/wiki/Three.js-Shading-Language> — "Currently `NodeBuilder` has two extended classes, the `WGSLNodeBuilder` aimed at WebGPU and `GLSLNodeBuilder` aimed at WebGL2."

<a id="three-a04"></a>**THREE-A04** (CONFIRMED) — `WGSLNodeBuilder` emits bind-group bindings and vertex-buffer layouts alongside shader text, and emits `enable <directive>;` (subgroups, subgroups-f16, f16, clip_distances, dual_source_blending) only when a node requests it. Source: <https://raw.githubusercontent.com/mrdoob/three.js/dev/src/renderers/webgpu/nodes/WGSLNodeBuilder.js> — "A node builder targeting WGSL. This module generates WGSL shader code from node materials and also generates the respective bindings and vertex buffer definitions."

<a id="three-a05"></a>**THREE-A05** (CONFIRMED) — Render pipelines are cached under vertex-program id + fragment-program id + backend render cache key; programs are reused across pipelines; pipelines are reference-counted and released at `usedTimes === 0`. Source: <https://raw.githubusercontent.com/mrdoob/three.js/dev/src/renderers/common/Pipelines.js> — `stageVertex.id + ',' + stageFragment.id + ',' + this.backend.getRenderCacheKey()`.

<a id="three-a06"></a>**THREE-A06** (CONFIRMED) — Bind-group layouts are deduplicated through a cache keyed on the combination of layout entries. Source: <https://raw.githubusercontent.com/mrdoob/three.js/dev/src/renderers/webgpu/utils/WebGPUBindingUtils.js> — "A cache that maps combinations of layout entries to existing bind group layouts."

<a id="three-a07"></a>**THREE-A07** (CONFIRMED) — Command encoding is per render context / compute group (beginRender creates the encoder, finishRender finishes and submits); submission reuses a module-scoped single-element array (r185 "Optimize submit() calls", #33513). Source: <https://raw.githubusercontent.com/mrdoob/three.js/dev/src/renderers/webgpu/utils/WebGPUUtils.js> — "Submits a single GPU command to the device queue using a shared, module-scoped array to avoid per-call array allocations." Also <https://raw.githubusercontent.com/mrdoob/three.js/dev/src/renderers/webgpu/WebGPUBackend.js>.

<a id="three-a08"></a>**THREE-A08** (CONFIRMED) — r185 introduced dedicated, cached descriptor classes with `reset()` (render pipeline, pipeline layout, command encoder, render-bundle encoder, …) to cut per-frame allocation. Source: <https://github.com/mrdoob/three.js/pull/33525> — "caches the descriptor instances whenever possible to reduce per frame object allocation and GC overhead."

<a id="three-a09"></a>**THREE-A09** (PLAUSIBLE) — Post-processing is a node graph: `RenderPipeline` (renamed from `PostProcessing` in r183) takes an `outputNode` chain, has built-in MRT support and automatically combines passes; `EffectComposer` is unsupported on `WebGPURenderer`. Source: <https://threejs.org/manual/en/webgpurenderer.html> — "`WebGPURenderer` comes with a new post-processing stack with built-in Multiple Render Targets (MRT) support and automatic pass combination thanks to the node material." (The r183 rename is from the manual, not re-derived from the r183 changelog.)

<a id="three-f01"></a>**THREE-F01** (CONFIRMED) — r185 added `ClusteredLighting` (Forward+): screen tiles × exponential depth slices, compute-built per-cluster light lists (defaults 32 px tiles, 24 slices, 64 lights/cluster, 1024 lights); `TiledLighting` was removed in the same release (#33751). Source: <https://github.com/mrdoob/three.js/pull/33406> — "partitions the view frustum into a 3D cluster grid (screen tiles × exponential depth slices)"; <https://github.com/mrdoob/three.js/releases/tag/r185>.

<a id="three-f02"></a>**THREE-F02** (CONFIRMED) — r184 added `DynamicLighting` (#33042): analytic lights batched into uniform arrays so light-count changes do not recompile materials (defaults 8 directional / 16 point / 16 spot / 4 hemisphere). Source: <https://threejs.org/docs/pages/DynamicLighting.html> — "A custom lighting implementation that batches supported analytic lights into uniform arrays so light count changes do not recompile materials."; <https://github.com/mrdoob/three.js/pull/33042>.

<a id="three-f03"></a>**THREE-F03** (CONFIRMED) — r185 restored WebXR on the WebGPU backend (#33583, funded by Meta); `XRManager.getWebGPUBinding()` and a `multiview` renderer option exist. Source: <https://github.com/mrdoob/three.js/pull/33583> — "This PR brings the implementation back. Currently only WebGL is supported for WebXR."

### 2.2 luma.gl 9 / deck.gl 9 (visgl)

**Latest versions:** luma.gl 9.4.0-beta.6 (published 2026-09-02; 9.4 whats-new targets August 2026); luma.gl 9.3 (2026-03-31); deck.gl 9.3.11 still pins luma.gl 9.3, deck.gl 9.4 is in alphas ([C19](#c19); <https://registry.npmjs.org/@luma.gl/core>, <https://registry.npmjs.org/deck.gl>).
**What changed architecturally:** 9.4 moved all draw state (pipeline, bindings, vertex arrays, direct/indirect draws, render bundles) onto `RenderPass`; unified WGSL assembly with `@binding(auto)`, hook functions and named injections; an experimental frame-graph (`GPUCommandGraph`), GPU scene draw generation, GPU virtual-geometry selection, a splats package, a WebGPU-first post-processing set, WBOIT, integer-controlled fp64 on Apple adapters, and a packed-binary64 subtraction helper.

<a id="luma-a1"></a>**LUMA-A1** (CONFIRMED) — The command model is deferred on WebGPU (CommandEncoder → finish() → CommandBuffer → submit()) and effectively immediate on WebGL under the same API shape. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/api-guide/gpu/gpu-commands.md> — "On WebGPU, command encoding is truly deferred. … On WebGL, luma.gl preserves the same API shape where practical, but rendering remains effectively immediate."

<a id="luma-a2"></a>**LUMA-A2** (CONFIRMED) — In 9.4 all draw state moved from `RenderPipeline` onto `RenderPass`; the old APIs are deprecated compatibility paths. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/whats-new.md> — "`RenderPass` now owns pipeline, binding, vertex-array, direct-draw, indirect-draw, and render-bundle commands. The former `RenderPipeline` draw and binding APIs remain as deprecated compatibility paths."

<a id="luma-a3"></a>**LUMA-A3** (CONFIRMED) — `PipelineFactory` caches pipelines per device keyed by a hash of pipeline inputs plus device type, with reference counting and a retain-at-zero policy. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/api-reference/core/pipeline-factory.md> — "When the reference count reaches zero, the pipeline is either destroyed or retained depending on `device.props._destroyPipelines`."

<a id="luma-a4"></a>**LUMA-A4** (CONFIRMED) — WGSL is assembled as ONE unified source with all entry points; modules declare `@binding(auto)`, rewritten to concrete numbers before reflection/compile; app bindings from 0, module bindings from 100+. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/api-reference/shadertools/wgsl-support.md> — "Shadertools rewrites `@binding(auto)` to concrete binding numbers before the final WGSL is reflected and compiled by WebGPU."

<a id="luma-a5"></a>**LUMA-A5** (PLAUSIBLE) — 9.4 adds WGSL hook functions and named injections (`vs:#main-start`, `fs:#main-end`) plus a `ShaderPlugin` unit; the preprocessor accepts numeric/boolean `#if` and capability defines evaluated before binding assignment. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/whats-new.md> — "`ShaderAssembler` now applies registered hook functions and standard named injections such as `vs:#main-start` and `fs:#main-end` while assembling unified WGSL shaders." (The numeric-`#if`/capability-define detail is from the same page's surrounding text, not an independent source.)

<a id="luma-a6"></a>**LUMA-A6** (CONFIRMED) — `GPUCommandGraph` is a frame-graph: fixed-capacity buffer/texture resources plus ordered compute/render/copy nodes; declared uses drive ordering and transient lifetime; compile once, `encode()` each frame into the caller's encoder. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/api-reference/experimental/gpu-core/gpu-command-graph.md> — "GPUCommandGraph<Parameters> declares fixed-capacity WebGPU buffer and texture resources plus ordered compute, render, and copy nodes."

<a id="luma-p1"></a>**LUMA-P1** (CONFIRMED) — 9.4 adds render bundles (WebGL2-unsupported); rebuild on command-list / bound-resource / pipeline / attachment-compatibility change, not on buffer/texture content change. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/api-reference/core/resources/render-bundle-encoder.md> — "Render bundles allow expensive CPU-side command recording and validation to be performed once and reused, improving performance when many identical draw calls are repeated frame after frame."

<a id="luma-p2"></a>**LUMA-P2** (CONFIRMED) — 9.4.0-alpha.1 skips redundant uniform-buffer writes in core. Source: <https://github.com/visgl/luma.gl/releases/tag/v9.4.0-alpha.1> — "fix(core): Avoid redundant uniform buffer writes (#2644)".

<a id="luma-p3"></a>**LUMA-P3** (CONFIRMED) — Portable timestamp `QuerySet` gated on `device.features.has('timestamp-query')`, backed by `EXT_disjoint_timer_query_webgl2` on WebGL, results asynchronous. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/api-reference/core/resources/query-set.md> — "Timestamp queries are portable when `device.features.has('timestamp-query')` is `true`. On WebGL this is backed by [`EXT_disjoint_timer_query_webgl2`]."

<a id="deck-p4"></a>**DECK-P4** (CONFIRMED) — deck.gl 9.4 picking uses `instance_index` instead of per-object picking colours for most layers. Source: <https://raw.githubusercontent.com/visgl/deck.gl/master/docs/whats-new.md> — "Picking has been optimized. Most layers now use shader builtins (`instance_index`) instead of picking color buffers, reducing GPU memory usage and layer initialization costs."

<a id="luma-f1"></a>**LUMA-F1** (CONFIRMED) — `GPUSceneDrawGeneration` converts visible `GPUScene` records into bounded indirect draw commands on the GPU; requires `indirect-first-instance`; WebGPU has no portable bindless multi-draw, so one indirect draw per command slot. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/api-reference/experimental/gpu-core/gpu-scene-draw-generation.md> — "`GPUSceneDrawGeneration` turns active, visible `GPUScene` records into bounded indirect draw commands."

<a id="luma-f2"></a>**LUMA-F2** (CONFIRMED) — GPU virtual-geometry selection: bounding-sphere frustum culling plus a screen-space-error metric refines a hierarchy whose cluster IDs may be meshlets, point-cloud nodes, impostors or terrain patches; counts feed indirect draws. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/api-reference/experimental/gpu-core/gpu-virtual-geometry-selection.md> — "Cluster IDs can address meshlets, point-cloud nodes, impostors, terrain patches, or application-defined geometry records."

<a id="luma-f4"></a>**LUMA-F4** (PLAUSIBLE) — `@luma.gl/splats` renders Gaussian splats GPU-natively on WebGPU (project, sort, draw per streamed batch through a command graph; bounded residency, hierarchy traversal, foveated LOD, GPU picking); WebGL2 gets only a prepared `SplatRenderer` path. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/api-reference/splats/README.md> — "The graph renderer, GPU ordering, hierarchy traversal, and storage-backed features require WebGPU. Use the prepared SplatRenderer path when WebGL 2 compatibility or caller-provided source ordering is required." (Beta-stage package; the feature list is from its README, not from an executed run.)

<a id="luma-f5"></a>**LUMA-F5** (CONFIRMED) — 9.4 ships a WebGPU-first composable post-processing set (depth-aware blur, SSAO, temporally stabilised GTAO, SSGI, outlines, TAA, motion blur, temporally stabilised SSR, height fog, clustered volumetric lighting, GPU-driven adaptive exposure, HDR-safe multiscale bloom). Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/whats-new.md> (line 194, "## Version 9.4") — "New WebGPU-first composable pipelines provide depth-aware blur, SSAO, temporally stabilized GTAO, colored screen-space diffuse global illumination, outlines, temporal AA, motion blur, roughness-aware temporally stabilized screen-space reflections, compact height fog, bounded clustered participating-media lighting with camera-aware history, GPU-driven adaptive exposure, and HDR-safe successively filtered multiscale bloom."

<a id="luma-f6"></a>**LUMA-F6** (CONFIRMED) — Experimental WBOIT renderer on WebGPU and WebGL2 with two `rgba16float` accumulation/revealage targets; A-buffer renderer as the alternative. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/api-reference/experimental/wboit-renderer.md> — "WBOITRenderer implements weighted blended order-independent transparency on WebGPU and WebGL2."

<a id="deck-g1"></a>**DECK-G1** (CONFIRMED) — deck.gl compensates for missing f64 with a viewport-determined dynamic translation of common-space positions; offset coordinate systems trade accuracy for a linearised local projection. Source: <https://raw.githubusercontent.com/visgl/deck.gl/master/docs/developer-guide/coordinate-systems.md> — "To compensate for the lack of 64-bit floats in WebGL2/WebGPU, deck.gl may apply a dynamic translation to common-space positions, determined by the viewport, to improve the precision of projection."

<a id="luma-g2"></a>**LUMA-G2** (CONFIRMED) — luma's fp64 is double-single (hi+lo f32, ~48 significant bits); the full function library is GLSL-only; WGSL gets only `fp64arithmetic` (add/sub/mul/div/sqrt). Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/api-reference/shadertools/shader-modules/fp64.md> — "The full `fp64` function library is GLSL-only. It does not provide WGSL source, so WGSL shaders cannot call `exp_fp64`, `log_fp64`, or its trigonometric functions."

<a id="luma-g3"></a>**LUMA-G3** (CONFIRMED) — On Apple WebGPU adapters luma switches double-single arithmetic to integer-controlled `twoSum`/`twoProd`/renormalisation because the Metal compiler may reassociate/fuse float ops; `LUMA_FP64_INTEGER_ARITHMETIC` forces or disables it. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/whats-new.md> — "WGSL double-single arithmetic automatically uses integer-controlled `twoSum`, `twoProd`, and renormalization on Apple WebGPU adapters, avoiding Metal compiler reassociation while retaining the existing `vec2f` API."

<a id="luma-g4"></a>**LUMA-G4** (CONFIRMED) — Large-coordinate rendering needs one exact operation — `localPosition = round_f32(exact(worldPosition - worldOrigin))` — implemented by subtracting packed binary64 significands/exponents with integer ops in WGSL and rounding once. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/api-guide/shaders/gpu-floating-point-precision.md> — "Large-coordinate rendering often does not need general fp64 arithmetic. It needs this operation: `localPosition = round_f32(exact(worldPosition - worldOrigin))`".

<a id="luma-t1"></a>**LUMA-T1** (CONFIRMED) — Resource `id` is copied into the WebGPU object `label`; `luma.log` offers persistent debug flags/log levels; WebGL dev-tools/Spector.js integration lives behind a separate `@luma.gl/webgl/debug` entry. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/developer-guide/debugging.md> — "`id` is copied into the WebGPU object `label` field which is designed to support debugging".

<a id="luma-t2"></a>**LUMA-T2** (PLAUSIBLE) — `SnapshotTestRunner` does browser-driven golden-image pixel diffs with tolerance/threshold; deck.gl enabled render tests on WebGPU in the 9.4 alphas; luma 9.4 adds feature-level-specific WebGPU test devices. Source: <https://raw.githubusercontent.com/visgl/luma.gl/master/docs/api-reference/test-utils/snapshot-test-runner.md> — "pixel-diffing with a pre-defined 'golden image'". (The deck.gl alpha render-test enablement is from the deck.gl releases page, <https://github.com/visgl/deck.gl/releases>, not re-derived from a PR.)

### 2.3 The WebGPU platform (W3C, Dawn, wgpu, WebKit)

**Latest versions:** WebGPU API W3C Candidate Recommendation Draft 2026-09-01; WGSL CRD 2026-08-31; Chrome 152 stable 2026-08-25; Firefox 155 2026-09-01; Safari 26.2 2025-12-12; wgpu v30.0.0 2026-07-01.
**What changed architecturally:** both specs reached CR; language extensions are runtime-detected via `navigator.gpu.wgslLanguageFeatures`; Compatibility Mode shipped (Chrome 146); Immediates (push-constant equivalent) shipped (Chrome 149-150); transient attachments, `linear_indexing`, `subgroup-size-control`, `texture-formats-tier1/2`, `primitive_index` and dual-source blending (Firefox) shipped; bindless is a Draft proposal with a live Dawn prototype; multi-view is being redesigned; mesh shaders and f64 remain Milestone 4+.

<a id="wgpu-01"></a>**WGPU-01** (CONFIRMED) — The WebGPU API is a W3C Candidate Recommendation Draft dated 1 September 2026. Source: <https://www.w3.org/TR/webgpu/> — "W3C Candidate Recommendation Draft, 1 September 2026".

<a id="wgpu-02"></a>**WGPU-02** (CONFIRMED) — WGSL is a CRD dated 31 August 2026 enumerating runtime-detectable language extensions (readonly_and_readwrite_storage_textures, packed_4x8_integer_dot_product, unrestricted_pointer_parameters, pointer_composite_access, uniform_buffer_standard_layout, subgroup_id, subgroup_uniformity, texture_and_sampler_let, texture_formats_tier1, linear_indexing, immediate_address_space, fragment_depth, buffer_view, swizzle_assignment) alongside enable-extensions (f16, clip_distances, dual_source_blending, subgroups, primitive_index, subgroup_size_control); authoring is feature-detected via `navigator.gpu.wgslLanguageFeatures`. Source: <https://www.w3.org/TR/WGSL/> — "W3C Candidate Recommendation Draft, 31 August 2026".

<a id="wgpu-03"></a>**WGPU-03** (CONFIRMED) — `GPUFeatureName` now includes "subgroups", "texture-formats-tier1", "texture-formats-tier2", "primitive-index", "texture-component-swizzle", "subgroup-size-control", "texture-compression-unaligned" and "core-features-and-limits". Source: <https://gpuweb.github.io/gpuweb/> — `"core-features-and-limits" ... "subgroups" "texture-formats-tier1" "texture-formats-tier2" "primitive-index" "texture-component-swizzle" "subgroup-size-control" "texture-compression-unaligned"`.

<a id="wgpu-04"></a>**WGPU-04** (PLAUSIBLE) — Chrome 146 (2026-02-25) shipped Compatibility Mode (`featureLevel: "compatibility"`) on OpenGL ES 3.1-class hardware. Source: <https://developer.chrome.com/blog/new-in-webgpu-146> — "This mode lets you run WebGPU on older graphics APIs like OpenGL ES 3.1." ## 5. What NOT to copy, and why

1. **A TSL-style single-source shader layer** ([THREE-A03](#three-a03), [C20](#c20)). It would remove the dual-authoring cost, but it is a C17-scale rewrite of ~110 GLSL and ~100 WGSL files, it conflicts with the ratified template that WebGPU shaders are pre-translated twins, never runtime-generated (`ARCHITECTURE.md:838-870`), and it would void every pixel-parity baseline at once, which the proof bar (R-2026-08-29-1) cannot certify in a wave. NASA 3DTilesRendererJS is paying that migration cost now. Keep Principle 5 plus lockstep spec pairs; adopt only the derived pieces (G3 `enable` emission, binding ranges).
2. **deck.gl's per-viewport common-space rebase** ([DECK-G1](#deck-g1)). It is a weaker precision model than per-vertex high/low RTE and linearises the local projection; a planet-scale globe cannot accept it. The fork's rule stays.
3. **Compatibility Mode as the WebGL replacement** ([WGPU-04](#wgpu-04), [WGPU-05](#wgpu-05)). Compat forbids vertex-stage storage buffers (instances, splats, flow field, skinning all use them), per-attachment blend state (MRT OIT), partial array-layer views (CSM), and `textureLoad` on depth. Principle 1 keeps WebGL working; compat is a probe leg and possibly an AUTO attempt, never a fallback replacement.
4. **The TSL software rasterizer** ([C22](#c22)). The fork's own research verdict (`DEFERRED_WORK.md:4622`) rejected Tier-3 visbuffer/software raster on browser WebGPU for want of 64-bit atomics; three.js demonstrates the packed-32-bit route, which is worth one re-examination inside `MS-00`, not a track.
5. **`instance_index`-only picking** ([DECK-P4](#deck-p4)). Cesium pick identity is per-feature (3D Tiles feature IDs, metadata, drillPick, snap), not per-instance; FAR-409's integer-attachment plan is the right shape. Do not replace the pick-ID contract with a layer-local index.
6. **Per-context encoder + per-pass submit** ([THREE-A07](#three-a07)). The fork already has one frame encoder with a single main submit; three.js's model would multiply submissions. Take only the allocation-free submit helper and fold the 51 side submits, as FAR-402 plans.
7. **Silent WebGPU→WebGL fallback** ([THREE-A01](#three-a01)). `ContextFactory.ts:220-306` warns and offers `strictRenderer`; the Logging doctrine requires the fallback to reach the console. Keep the warning.
8. **Bindless on a Canary flag** ([WGPU-16](#wgpu-16), [WGPU-17](#wgpu-17)). Draft proposal, prototype in Dawn, no ship date; the fork's exposure is a reserved `ShaderDefineHi` bit and `texture_and_sampler_let` groundwork behind G3, not a resource-table implementation.
9. **Reference counting that replaces LRU** ([THREE-A05](#three-a05), [LUMA-A3](#luma-a3)). Refcounts alone leak under the fork's long-lived feature renderers (the WebGL `ShaderCache` needs deferred destruction for the same reason); add refcounts beside the LRU and let the LRU be the backstop.
10. **luma's separate debug entry bundle** ([LUMA-T1](#luma-t1)). The fork's pragma stripping already yields zero-cost debug removal across `.js` and `.ts`, and the build-variant system already has three entry barrels; a fourth debug barrel adds packaging surface for no measured size win.
11. **Mesh shaders in any form** ([WGPU-18](#wgpu-18)). Milestone 4+; `MS-16` is dormant by construction and stays so.
