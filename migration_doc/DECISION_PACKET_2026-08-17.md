## P1 — Charter §3.5 "house scale": ratify the softening, reject it, or calibrate it (lane charter / D-A)

**The question.** OBJECTIVE FIRST — the goal is REVIEWABILITY OF THE INSTRUMENT FLEET: that a reviewer can read a gate and tell whether it is sound, and that shape-validation logic lives in one shared home instead of N private ones. **The objective, as distinct from the instrument.** Ratifying or rejecting the prose is arguing about the instrument. The goal is served by (a) calibrating the trigger to the metric the audit actually used, and (b) making the shape-predicate duplication itself measurable — that is the finding, not the byte count.

## P5 — Sync drillPick on WebGPU: an unbounded loop, not a policy question (lane picking / D-H)

**The question.** OBJECTIVE FIRST — the instrument is "retire the `isWebGPU` branch at Picking.js:919 so Core Principle 2 is satisfied." Satisfying only that would mean swapping `isWebGPU` for `supportsSynchronousReadback` and leaving both the pragma-stripping and the unbounded loop in place — a green principle check over a hang. The OBJECTIVE is that a developer calling a documented public method either gets the right answer or is told it cannot be given. Does the identity-plateau predicate govern `drillPick`: adopt it, declare sync drillPick unsupported through the readiness union, or make drillPick async-only?

**The objective, as distinct from the instrument.** On WebGPU, sync drillPick cannot give the right answer at all: it requires N sequential render-then-read round-trips inside one task, the same physical boundary that makes `WebGPUContext.readPixels` a null-returning shim. Naming that boundary in the readiness union, rather than approximating around it, is what serves the objective — and the async sibling that ships today with zero consumers is the thing that actually restores the capability.

**Evidence.**

Reading the loop changes the question. `drillPick(pickCallback, limit)` (Picking.js:1825-1848) has NO iteration bound: `while (defined(pickedResults) && pickedResults.length > 0)`, terminating only on an empty pick or `results.length >= limit`, and `limit` defaults to `Number.MAX_VALUE` (:1830-1832). `addDrillPickedResults` (:1770-1822) does not deduplicate — it pushes the same object again every iteration. Inside that loop, on WebGPU, the cache CANNOT refresh: `_startReadback` returns immediately while `_readbackInFlight` is true (WebGPUPickFramebuffer.ts:1274-1277), and the mapAsync continuation is a microtask that cannot run until the synchronous loop finishes (:1339-1372). The view provenance is IDENTICAL across iterations by construction — the camera does not move, and `getCenterPixelViewProvenance` deliberately excludes the frame number (Picking.js:1550-1552) while the ordinary path passes no owner (:1662-1666), so the `show = false` mutations the drill loop performs are INVISIBLE to the gate. Therefore `end()`'s fast path (`_readbackRegionsEqual`, WebGPUPickFramebuffer.ts:735-748) returns the SAME bytes and the SAME object on every iteration, forever. Today that is usually masked: with a 3×3 aperture a cursor that moved more than 1 px since the cached readback fails `_extractPixelsFromCachedRegion`'s centre-containment test (:637-646), the pick returns `[]`, and the loop exits after one iteration — exactly the "empty after 1-2 iterations" symptom the Batch-184 warning describes (Picking.js:910-916). The mask fails whenever the cursor is INSIDE the cached aperture: a stationary hover, or a click at a just-hovered pixel. Exposure is not hypothetical: `packages/sandcastle/gallery/picking/main.js:128` calls `scene.drillPick(movement.endPosition)` with no limit on MOUSE_MOVE (:137), `star-burst/main.js:125` and `:334` do the same, and `Scene.pickAll` (Scene.js:5475-5481) hard-defaults `limit` to `Number.MAX_VALUE`. CONFIRMED BY READING, UNVERIFIED AT RUNTIME — no browser was run. What would settle it: a Playwright probe on `?renderer=webgpu` loading the picking gallery demo, hovering to warm the cache, then holding the cursor still for one more mousemove, under a hard watchdog — which under P4 queues in the orchestrator's serialized probe lane. THE COUPLING TO P7 IS DECISIVE: widening the capture aperture is precisely the change that makes `_extractPixelsFromCachedRegion` succeed during cursor motion, which REMOVES THE MASK.

**Options.**

### A. Adopt the predicate for drillPick

Let drill iterations serve from cache when conditions (a)-(f) hold, as ordinary picks will.

- **Pros —** One policy everywhere; no special case in the Scene layer; retires the `isWebGPU` branch cleanly.
- **Cons —** The predicate proves invariance under POSE uncertainty. Drill's mutation is a CONTENT change at zero pose delta, so conditions (b)-(e) are all trivially satisfied and only condition (f) — the scene-content revision bump — can decline. No content-revision counter exists in the engine today. Adopting the predicate as specified therefore does not merely fail to fix the loop, it BLESSES it: every iteration presents as a valid proof-carrying serve.

### B. Declare sync drillPick unsupported on non-sync-readback backends

Branch on `context.supportsSynchronousReadback` (never `isWebGPU`), return `[]`, set `lastPickInfo` to `declined('sync-drill-requires-synchronous-readback')`, make the warning PERMANENT (it is pragma-stripped today at Picking.js:917-929) and point at `drillPickAsync`.

- **Pros —** Honest about a structural impossibility. Preserves the upstream array signature so nothing throws; fixes LD-09's two defects (pragma-stripped, backend-identity branch) in the same edit; removes the hang by removing the serve; needs no new machinery.
- **Cons —** A visible behaviour change: the two gallery demos and any app relying on warm-cache drill go from "sometimes returns a layer" to "always empty," so those demos must be repointed to `drillPickAsync` in the same change or the fork ships broken examples. Loses the one case that genuinely worked (single-layer drill at a warm stationary cursor).

### C. Async-only: deprecate the sync path

Keep `Scene.drillPick`'s signature, emit a permanent deprecation, delegate to option B's behaviour; migrate docs, demos and `Scene.pickAll` to the async siblings that already ship (Scene.js:5248, Picking.js:1869).

- **Pros —** Ends the class of problem rather than bounding it; `drillPickAsync` awaits every iteration and is correct on BOTH backends by construction; the async API already ships, is spec-covered, and has zero consumers — this is the consumer.
- **Cons —** Deprecating an upstream method is a fork divergence with real merge cost; WebGL's sync drillPick is correct today and would be deprecated for a WebGPU-only reason; every downstream app using drillPick must change code, which the dual mandate says to avoid where possible.

- **Cons —** Result on WebGPU is still `[]` in practice, so it converges on option B's outcome while carrying extra state; a sentinel that fires is a bug report, not a fix, and could mask the real defect if someone reads it as handled.

**Recommendation.** B plus D's sentinel, with C as the stated direction. ## P7 — Pick capture aperture and the frame-age cap: two numbers that must be ruled together (lane picking / D-D + D-E)

**The question.** TWO SEPARABLE RULINGS, PACKAGED AS PAIRS — you may mix any aperture with any cap. (D) How wide should the WebGPU synchronous pick capture aperture be (today 3×3), given that the identity-plateau predicate ruled admissible by R-2026-08-17-3 cannot evaluate at all inside a 3×3 window? (E) What is the hard frame-age cap on a served pick, in what UNITS, and should R-2026-08-17-11's caller-opted-in `available` mode get a looser cap than `auto`?

**The objective, as distinct from the instrument.** §D instrument: "make the plateau predicate non-vacuous" → 33×33. Objective: a user who clicks or hovers while the camera moves gets the right answer instead of nothing → 63×63, because it is free and covers drag at k=1. Both sizes are honest that NO aperture recovers picking at 30°/s with k=2 — the physics forbids it without synchronous readback, and the correct answer there is fail-closed plus the async path (investigation :148); no doc or release note may imply otherwise. §E instrument: "pick a number that makes the predicate provable." Objective: a served pick names an object that is STILL THERE, still visible, still under the cursor. Frame age is a weak proxy for all three — it bounds camera drift indirectly (epsilon does that better) and content change poorly (only a revision counter does that). The cap should be sized and named as a CONTENT-change bound, and the real work is condition (f), a scene-content revision token, currently unbuilt and untracked.

**Evidence.**

§D EVIDENCE. The pick rectangle is ONE number doing three jobs. `computePickingDrawingBufferRectangle` (Picking.js:1560-1571) defaults `width = 3.0`; that rect becomes (a) the screen-space cull volume via `getPickCullingVolume`/`getPickPerspectiveCullingVolume` half-extents (Picking.js:1481-1520, scaling linearly with width/height), (b) the render scissor (WebGPUPickFramebuffer.begin copies it into `_passState.scissorTest.rectangle`, :400-404, and into `pickScissor`, :527-532), and (c) the readback region and decode window (`_captureReadbackRegion` :556-565; `pickObjectsFromPixels` spirals outward from the centre and returns the FIRST hit under `limit=1`, :117-184). Because of (c), naively passing width=33 changes `scene.pick`'s documented semantics: hit tolerance goes from ±1 px to ±16 px, so a click on empty sky 16 px from a billboard would select the billboard. Capture MUST therefore be decoupled from the query rect — the investigation said "returned rect unchanged" (PICK_DURING_MOTION_INVESTIGATION_2026-08-14.md:109) but nothing in code separates them today. The doc's cost figure is wrong in both directions: WebGPU pads `bytesPerRow` to 256 (WebGPUPickFramebuffer.ts:837, :1291), so 3×3 actually costs 768 B (not 36 B) and 33×33 costs 8,448 B (not ~4 KB) — 11×, not 117×. Any width ≤ 64 px rounds to the same 256-byte row, so widening horizontally is FREE up to 64: 63×63 costs 16,128 B, 65×65 jumps to 33,280 B. At the worst realistic sync-pick rate — DOM mousemove, which Cesium does not coalesce (ScreenSpaceEventHandler.js:126 dispatches inline) — 60 picks/s costs 45 KiB/s at 3×3, 495 KiB/s at 33×33, 945 KiB/s at 63×63. Sync-pick-per-hover consumers are the 3D Tiles inspector (Cesium3DTilesInspectorViewModel.js:31 and :403, both MOUSE_MOVE) and gallery demos; the flagship Viewer uses sync pick on LEFT_CLICK / LEFT_DOUBLE_CLICK only (Viewer.js:1164, :1169, :1173). DERIVED HERE from the investigation's own rotation term (eps = f·omega/60 px/frame, f = 1662.8 at 1920×1080/60°) under conditions (c)+(d) — the reprojected point must sit inside the aperture AND a plateau disc of radius 2·eps must fit around it, i.e. halfWidth ≥ (k+2)·eps — max serveable rate is 0.5°/s at 3×3, 6.2°/s at 25×25, 8.3°/s at 33×33, 16.0°/s at 63×63 (all k=2); the 33×33 figure reproduces the investigation's stated "~7°/s" within its own rounding, validating the model. UNVERIFIED AND LOAD-BEARING: the cull-cone and scissor cost of widening — the investigation demanded it be measured (:109) and it never was; GlobeSurfaceTileProviderRendering.js comments claim the 3×3 rect drops pick-render cost by 90-95%, an unsourced claim about the same term. §E EVIDENCE. The three existing constants count DIFFERENT CLOCKS, which the doc's "4 / 8 / 2" comparison hides. `PickDepth`'s `ASYNC_DEPTH_MAX_STALE_FRAMES = 4` (PickDepth.js:29) counts RENDERED frames (`_updateCount` incremented inside `update()` on the async branch, :144, comment at :138-142). `WebGPUPickFramebuffer`'s `CENTER_PIXEL_MAX_STALE_FRAMES = 4` (:28) counts PICK PASSES (`_updateCount` incremented in `begin()`, :393; field comment at :327 says "Measured in picks, not wall"). `WebGPUSnapFramebuffer` bounds BOTH: `MAX_PRIOR_QUERY_AGE = 8` and `MAX_PRIOR_SCENE_FRAME_AGE = 8` (:160-161), with the reason stated at :156-159 — "query count alone would let a payload survive arbitrarily many animation/tile/model frames when snap() is idle." NONE of the three is measured: PickDepth's 4 arrives in Batch 252 (f1b4d43f77) from a one-frame observation; the centre-pixel 4 in Batch 285 (55c9a136bf), same 4×-over-one-frame judgement; Snap's 8 is the only one with a written derivation ("Eight frames/calls covers ordinary 1-3 frame map latency with margin") and that observation is itself unrecorded. Snap also caps cursor motion at `MAX_PRIOR_CURSOR_DELTA_PIXELS = 2` (:166) despite its 25×25 aperture (:162-165: a partially overlapping aperture "cannot prove what lies in its missing stripe"). CORRECTION TO THE ARCHITECTURE DOC: its claim that "Snapping already runs 25×25 for exactly this reason" (§7.3) is FALSE — snap's 25 is upstream's search-radius default for finding edges and vertices (Snapping.js:336, :347, from upstream commit bc8d43fb8d), and snap's motion tolerance is 2 px, not 12. THE UNIT CHOICE IS LOAD-BEARING FOR P5: a drill loop runs N picks inside ONE rendered frame, so a pick-counted cap of 2 auto-expires drill iteration 3 while a rendered-frame cap of 2 never expires inside the loop at all.

**Options.**

### U1 — 33×33 fixed + single-clock cap of 2 (D-A + E-A)

Widen capture only (query rect stays 3×3) to 33×33 with the decode window centred 3×3 on the reprojected point; one constant `MAX_SERVED_PICK_AGE = 2`, same for every request mode, one unit (picks or rendered frames).

- **Pros —** Matches the number already reasoned about in the investigation; 8,448 B/pick, 495 KiB/s at 60 Hz — negligible; single constants, no new state; recovers the whole inertia decay and slow drag (≤ ~8°/s at k=2). The cap is the tightest of the three existing policies and defensible on the doc's grounds that a pick returns an identity rather than an interpolable scalar; one number to assert.
- **Cons —** Recovers nothing at real orbit-drag rates (30°/s needs 29 px of displacement headroom; 33×33 has 16); leaves half the free bandwidth budget unused; 121× wider cull cone with the cost still unmeasured. Whichever single unit you choose has a hole: pick-counted lets a cached ID survive arbitrarily many animation/streaming frames when picking is idle (the hazard Snap's comment names); rendered-frame-counted lets arbitrary drill iterations reuse one payload inside one frame — and the second hole is P5's hang.
- **Cost —** M — requires the capture/query decoupling (new field in PickReadbackRegion + a separate decode window). MUST land after P5.

### U2 — 63×63 fixed + dual clock, 2/2 for `auto`, ceiling 8/8 for `available` (D-B + E-B)

Same decoupling, sized at the 256-byte row boundary (63 px costs the same bytes/row as 33 px, only more rows). Adopt Snap's shape verbatim: bound BOTH pick-count age and rendered-scene-frame age; `auto` and `latest`-follow-on serve at ≤2/2, `available` serves up to 8/8 reporting `cached(ageFrames)`, beyond the ceiling both report `cold`. `ageFrames` names WHICH clock it reports (recommend the rendered-frame leg).

- **Pros —** Doubles the recoverable regime (16.0°/s at k=2, 21.4 at k=1 — reaches typical orbit drag at k=1) for 2× the bytes and ZERO change in row alignment; 945 KiB/s at 60 Hz still negligible; same code as U1, one different constant. The dual clock closes both holes with a precedent already shipped and reasoned about in-tree; makes `available` genuinely looser as the ruling's disclosure principle licenses without unboundedness; 8 matches the only constant in the fork with a written derivation; the pick-count leg is what bounds P5's loop at cap+1 iterations.
- **Cons —** 441× wider cull cone than 3×3 — the unmeasured term is twice as large as at 33×33; larger `_lastReadPixels` memcpy per serve (15,876 B, still trivial). Two constants and two counters to instrument and assert instead of one; 8 inherits Snap's unrecorded latency observation, so it is a BORROWED judgement not a measured one; `available` callers now see two distinct decline reasons.
- **Cost —** M — identical to U1, plus one interleaved A/B cull-cost leg (3×3 vs 33×33 vs 63×63) that P4 schedules into the serialized probe lane.

### U3 — Adaptive aperture from measured angular rate + unbounded `available` with disclosure only (D-C + E-C)

Size the capture per pick from recent pose-delta rate: 3×3 when static, widening toward 63×63 under motion. `auto` capped at 2; `available` serves whatever exists at any age, always disclosing `cached(ageFrames)`.

- **Pros —** Static hover pays 768 B and a 3-px cull cone; degrades to fixed cost only when motion needs it. Maximally faithful to "disclosure required when the CALLER decides" — the caller asked, the caller was told; no arbitrary ceiling to defend.
- **Cons —** The aperture must be chosen at CAPTURE time (frame k) but is needed at SERVE time (frame k+2) — you are predicting future motion, and a rate spike silently produces a too-small aperture; adds per-frame state and a second thing to instrument. The cost it optimises away is already negligible. And a pick ID is a REFERENCE, not a value: an arbitrarily old cached ID can name a primitive the app has since removed; `getObjectByPickColor` hands it back, and the generation tokens at WebGPUPickFramebuffer.ts:626-628 cover device/attachment change, NOT primitive lifetime — disclosure of age does not make a dangling reference safe.
- **Cost —** L — motion estimator in the pick framebuffer plus a new failure mode in the predicate's audit trail.

### U4 — Scene option, default 3×3 + drop the cap and rely on the epsilon ceiling (D-D + E-D)

Ship the widened aperture behind an opt-in flag with default behaviour byte-identical to today; delete the frame-age term as redundant against the plateau proof's reprojection-error ceiling (condition e).

- **Pros —** Zero risk to existing users; lets the widened path bake in the field before becoming default. One fewer arbitrary number; epsilon is derived from real pose delta rather than a frame count, and the predicate becomes purely geometric.
- **Cons —** Directly defeats R-2026-08-17-11, which made legacy `scene.pick()` map to `auto` precisely so existing callers GAIN the fix without code changes — a default-off aperture makes the predicate vacuous for every caller who does not know to flip it. Epsilon bounds CAMERA motion only: it is identically zero for a moving primitive under a static camera (P-3 / LD-16), a streamed-in tile, an animated model, a `show` toggle. Removing the cap leaves condition (f) as the sole guard and no content-revision counter exists, making the predicate strictly weaker than the string gate it replaces on the axis that gate accidentally got right.
- **Cost —** S to build, but permanently splits the tested surface and keeps LD-01/LD-02 unfixed by default.

**Recommendation.** U2, with three conditions. (1) Land the capture/query DECOUPLING first and assert it: the returned rect, the decode window and `pickObjectsFromPixels`'s spiral bound must stay at the caller's 3×3, or `scene.pick` silently becomes a 16-px-tolerance pick — a shippable semantic regression no test today would catch. (2) Do NOT widen before P5 lands: widening makes `_extractPixelsFromCachedRegion` succeed far more often, which is exactly the condition that turns sync `drillPick`'s current empty return into the unbounded loop. (3) The `ageFrames` unit must be documented precisely or it becomes the next "four incompatible readiness budgets." On the separate question of whether S6 should pull `PickDepth` down to 2: NO, and this contradicts §8's S6 framing — PickDepth's defect is not its 4, it is that the ±4 px window carries NO view provenance at all and is then reconstructed against the CURRENT frustum (LD-17, PickDepth.js:210-231); harmonising the number while leaving the missing provenance term produces a policy that LOOKS reconciled and is not. Costs of U2, stated plainly: the cull-cone term is the one real unknown and 63×63 makes it twice as large as 33×33 — I am recommending a size whose dominant cost is unmeasured, on the argument that bandwidth (the cost the doc worried about) is provably a non-issue below 1 MiB/s and the cull cone is measurable in ONE interleaved A/B leg (which P4 queues into the serialized lane). If that leg shows a real regression, 33×33 then 25×25 are graceful fallbacks and the constant is one line. Also: 8 remains a borrowed judgement — the honest fix is P-6's instrument measuring actual readback age k, which S0 already schedules and which should land before these numbers are frozen in JSDoc.

## P8 — Pick readiness API shape, and Globe.pickable's WebGPU-only divergence (lane picking / D-F + D-G)

The WebGL work is bounded and uses existing machinery: give the globe command a `pickId`, add the matching uniform to `createTileUniformMap` (GlobeSurfaceTileProviderRendering.js:495), and the generic derivation at DerivedCommand.js:288-320 works unchanged (it injects `out_FragColor = <pickId>` behind an `a == 0.0` discard, and globe fragments are opaque). 'globe' : 'undefined'` and :3560-3565 requires EVERY WebGL warmup attempt to report `resultKind === 'undefined'` with `resultPrimitiveIdentity === false`, while the probe explicitly sets `globe.pickable = true` (spec :4356 asserts that code shape). `probe-c10-11-mixed-coherence.mjs:57` also sets it true and `probe-c10-11-ddtd-hitrate.mjs:65` sets it false — the fleet is already routing around the divergence in both directions.

**Options.**

### V1 — Imperative verb + readiness getter/event, and mint globe pick IDs on WebGL (F-A + G-A)

`Scene.preparePickAsync(): Promise<PickReadiness>` plus `Scene.pickReady` (getter, delegating like `pickPositionSupported`) and `Scene.pickReadyEvent`; nothing in contextOptions. Separately attach a pick ID + uniform to the WebGL globe draw commands so `Globe.pickable = true` behaves identically on both backends, and update the S5 gate to assert AGREEMENT instead of divergence in the same commit.

- **Pros —** Covers both readiness use cases with upstream-shaped surfaces: the verb for prewarm-on-intent (the only thing that retires the retry loop), the getter/event for the passive question; matches the fork's four existing `*Async` Scene methods; keeps contextOptions a graphics-context bag; nothing to configure means nothing to configure wrong. The derivation machinery already exists; no new shader path.
