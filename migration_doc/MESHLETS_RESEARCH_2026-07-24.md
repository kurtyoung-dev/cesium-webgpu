**What it proves is possible in a browser today:**

- **Nanite-style virtualized geometry works on stock WebGPU without mesh shaders.** The whole runtime is compute passes + indirect draws: CullInstancesPass (per-instance frustum + occlusion) → CullMeshletsPass (per-meshlet frustum + occlusion + LOD cut, splitting survivors into HW/SW lists) → RasterizeHwPass "does a single drawIndirect()" / RasterizeSwPass "does a single dispatchWorkgroupsIndirect()" → RasterizeCombinePass → depth pyramid (src/passes/README.md). Device features requested: only `float32-filterable` (required) + `timestamp-query` (conditional); no raised limits, nothing exotic (src/utils/webgpu.ts).
- **Demo scale:** 640M tris (Jinx 120×120 instances), 1.7B tris (Lucy+dragons 70×70), 1.2B (bunnies 500×500), inside Chrome's default ~128MB storage-buffer binding limit. In dense scenes "Nearly 98% of the triangles are software rasterized, as it's much faster than hardware" (README). No formal ms timings published — "FPS might fluctuate due to the browser's enforced VSync".
- **The DAG build recipe** (in-browser, meshoptimizer + METIS WASM): partition current meshlets into METIS groups of 4 (GROUP_SIZE = 4, adjacency-constrained), simplify each merged group targeting a halving, re-split into ≤128-tri/≤64-vert meshlets, repeat to maxLods 20; stop when ≤1 meshlet remains or a level fails to remove enough triangles (src/meshPreprocessing/index.ts, src/constants.ts).
- **The monotonic-error schema** — the key reusable design piece: each meshlet stores maxSiblingsError, parentError, sharedSiblingsBounds, parentBounds; parent error = own simplification error + max(children's maxSiblingsError), so error strictly increases up the tree, siblings share bounds, and the root parentError is INFINITY. That makes the runtime LOD selection **traversal-free**: a per-meshlet parallel test, verbatim `return parentError > threshold && clusterError <= threshold;`, with model-space error projected via `(cotHalfFov * r) / sqrt(d2 - r*r)` scaled to screen height (src/passes/_shaderSnippets/nanite.wgsl.ts). This is philosophically identical to Cesium's geometricError→SSE math.

**Its documented limits (author's own words where possible):**

- **No 64-bit atomics in WebGPU is THE central constraint:** "WebGPU does not support atomic<u64>, so I had to compress data to fit into 32 bits (u16 for depth, 2×u8 for octahedron encoded normals)". Consequence: **no visibility buffer** — no room for cluster/triangle/material ID — so the SW-raster path outputs untextured normal-shaded pixels with acknowledged z-fighting from 16-bit depth.
- **One-pass occlusion only:** "just a depth pyramid from the previous frame's depth buffer. No reprojection and no two-pass" — disocclusion artifacts on fast camera motion are accepted.
- **Memory scaling is admittedly broken for production:** the drawn-meshlets buffer "allocates instanceCount * bottomLevelMeshletsCount * sizeof(vec2u) bytes" — the author calls this "not scalable". For 3D Tiles this is a direct warning: per-tile meshlet lists must be pooled/streamed, never statically allocated per instance.
- **Explicit not-implemented list, verbatim:** "No two-pass occlusion culling. No visibility buffer. No built-in shadows/multiview. No work queue in shaders. No VRAM eviction of unused LODs and streaming. No compression." Plus: no skinning, no materials in SW raster, per-meshlet backface cone culling "not finished".
- **Author's verdict:** the simplification quality and error metric are the unsolved production problems — "Unless you tackle simplification and error metric problems, you will end up with code similar to mine" — and he recommends implementing Wihlidal GDC 2016 ("Optimizing the Graphics Pipeline with Compute") and Aaltonen/Haar SIGGRAPH 2015 ("GPU-Driven Rendering Pipelines") first. That recommendation maps exactly onto the Tier 1 proposal in §5.

## 2. The WebGPU reality

- **No mesh shaders — and it does not matter.** Nanite's own runtime is compute-driven (GPU cluster job queue + SW raster for <32px triangles, "three times faster on average than the hardware rasterizer" — Karis/Stubbe/Wihlidal SIGGRAPH 2021 via thecandidstartup.org analysis); mesh shaders appear nowhere as a requirement. The pre-mesh-shader precedent is Aaltonen/Haar 2015 (AC Unity): 64-tri clusters, GPU cluster+triangle cull, index compaction, plain vertex shaders.
- **No 64-bit atomics — the one hard blocker, and only for Tier 3.** Nanite's visbuffer is a per-pixel 64-bit InterlockedMax (30b depth | 27b cluster | 7b triangle). Browser WebGPU has no path to it: nanite-webgpu's 32-bit pack costs materials entirely; Bevy 0.16's alternative (wgpu-native SHADER_INT64_ATOMIC / R64Uint texture atomics) is **native-only, explicitly unavailable in browsers** (jms55.github.io, wgpu PR #14623/#17765).
- **No multiDrawIndirect / drawIndirectCount in core WebGPU.** Only `chromium-experimental-multi-draw-indirect` exists behind the unsafe flag (Chrome 131 blog; gpuweb PR #2315 / issue #4349 open). The standard pattern: compute compacts a visible-meshlet list, then ONE drawIndirect with instanceCount = visible meshlets and vertex-pulling (instance_index → meshlet, vertex_index → meshlet-local triangle). Best practice: pack all indirect args in a single GPUBuffer — toji measured Chrome/D3D12 indirect validation dropping ~3ms → ~10µs (~300x).
- **Fork-local reality (anchored):**
  - `indirect-first-instance`, `subgroups`, `timestamp-query` are already in DESIRED_FEATURES and surfaced in the capability snapshot (WebGPUFeatureFlags.ts:52,56,59; WebGPUContext.ts:5548-5560) — but indirect-first-instance is "Detected, unused" (WEBGPU_MIGRATION_BACKLOG.md:651).
  - Zero multiDrawIndirect call sites in the fork; WebGPUIndirectDrawManager executes batches as a CPU loop of one drawIndexedIndirect per draw (WebGPUIndirectDrawManager.ts:252-274).
  - `maxBufferSize` is adaptively negotiated to 2GB, but `maxStorageBufferBindingSize` is snapshot-only — a meshlet mega-buffer bound as storage is capped at the ~128MiB default unless ADAPTIVE_LIMIT_CAPS grows an entry (WebGPUDevicePool.ts:103-126, :157-189, :713-741). Small (S) named prereq.
  - Flag-gated/contained scaffolding that a meshlet path must respect: GPU culling defaults to 'never' under FAR-003 containment (WebGPUContextCullerPool.ts:28-30) and the Hi-Z command-drop consumer is gated off pending FORK-41 (FEATURE_INVENTORY.md:587-588). A meshlet feature must define how it safely re-arms these — containment is correctness work, not a toggle to flip.

## 3. Where meshlets pay off for 3D Tiles — ranked for THIS fork

Framing: the historical "WebGPU 50% slower" deficit is closed (texture re-upload storm, ratio now ~0.98), so meshlets are an **offensive "where WebGPU should win" play on dense tilesets**, not a regression fix.

1. **Draw-call collapse (strongest fit).** The fork's own audit: the current 3D Tiles path "allocates per-tile and produces 1k-10k draw calls/frame with no cross-frame persistence" (PHASE_8_GPU_RESIDENT_TILES_DESIGN.md:50). This is precisely what the scaffolded indirect path was built for, and the substrate is unusually complete: WebGPUGPUCuller has CullMode.INDIRECT writing instanceCount=0 straight into indirect buffers (WebGPUGPUCuller.ts:6-8,38-45); WebGPUDrawCommand carries first-class drawIndirectBuffer/drawIndirectOffset (WebGPUDrawCommand.ts:186-188,616-625); render bundles synergize (bundle the indirect calls once, mutate only buffer contents per frame — WebGPURenderBundleManager.ts:1-15).
2. **Intra-tile cull granularity (second).** Today's GPU culler tests ONE bounding sphere per draw command — a huge photogrammetry b3dm is all-or-nothing. Meshlets (~128 tris + sphere + normal cone) are the missing finer granule, and meshopt's `computeMeshletBounds` returns exactly the coneApex/coneAxis/coneCutoff the cull compute consumes (node_modules/meshoptimizer/meshopt_clusterizer.d.ts:9-15,34-68).
3. **LOD smoothness (real but constrained — see the caveat).** Continuous cluster LOD **does not compose across 3D Tiles LOD levels**: a parent tile's geometry is an independent simplified asset with different vertices and no shared cluster boundaries, so a Nanite DAG cut cannot span the tile hierarchy without offline re-authoring of the tileset. Cluster LOD is achievable only intra-tile (per-tile mini-DAG softening pops within a tile's SSE band) or via non-standard content. No meshlet/cluster-LOD/GPU-driven extension was found in flight in CesiumGS/3d-tiles or 3d-tiles-tools (two targeted searches, 2026-07-24) — **UNCONFIRMED that any is being drafted**; absence-of-evidence, not proof. Consequence: meshletization must be a runtime/client-side concern for standard tilesets.
4. **Sub-pixel-triangle efficiency (weakest fit).** This is the SW-raster half of Nanite, blocked on the visbuffer problem (§2) and least valuable for a globe engine whose tile SSE traversal already keeps triangle density roughly bounded per screen area.

**Precedent inside the fork:** WebGPUPointCloudLODProcessor + WebGPUPointCloudRenderer are a shipped end-to-end instance of the exact Tier-1 shape — compute cull + LOD + compaction into visibleIndices + atomic visibleCount + drawIndirect, with subgroup variant and fallback (WebGPUPointCloudLODProcessor.ts:1-79; WebGPUPointCloudRenderer.ts:2049-2071). Zero new dependencies for meshlet building: meshoptimizer@1.1.0 (MIT, Arseny Kapoulkine) is already installed with MeshoptClusterizer AND MeshoptSimplifier (packages/engine/package.json:51; ThirdParty.json:132-137 — note doc says 1.2.0 vs installed 1.1.0, minor drift), and the lazy-WASM loading pattern already exists in GltfBufferViewLoader.js:15-22. **No shipped "3D Tiles through Nanite" precedent exists anywhere** (Cesium for Unreal changelog v1.7.0→v2.28.0: zero Nanite entries; only community demand threads) — this is genuinely novel ground, not catch-up. UNCONFIRMED that any 3D Tiles engine builds meshlet data from streamed tiles at runtime today.

**Scope boundary:** meshlets apply to exactly one of the fork's four tiles content families — triangle-mesh Model content (b3dm/i3dm/glTF via WebGPUModelRenderer). Point clouds already have their own compute-LOD/indirect path; Gaussian splats have their own sort/raster model; Vector3DTile classification is stencil-volume based. All scope statements must say Model-content-only.

## 4. What breaks — each with a story or an explicit v1 exclusion

- **Picking (survives with one mandatory fix).** Feature IDs for the common b3dm case are "packed into a storage buffer indexed by vertex_index" (WebGPUModelFeatureId.js:10-11). Meshlet draws re-index geometry, so `vertex_index` no longer equals the original vertex index — the meshlet VS must fetch the original index from the meshopt remap buffer before indexing the feature-ID buffer, or per-feature picking **silently degrades** to primitive-granularity colors. This exact silent-degradation failure already happened once (Batch 141 UBO-offset bug, WebGPUModelFeatureId.js:20-45) — it is the regression template for the meshlet pick probe.
- **Styling (same fix covers it).** Styling rides the same featureID→batch-texture path as picking; per-feature show/hide is fragment-side and survives HW raster. GPU-side styling remains Phase 8b's separate "WGSL styling compiler" item.
- **Classification (explicit v1 EXCLUSION).** The classification stack is stencil-volume based and partially scaffolded (WebGPUTranslucentTileClassification is the CLAUDE.md Principle-7 origin story). Classified tilesets keep the current non-meshlet path; meshlet-culling a tileset that *receives* classification is fine as long as depth is written by the normal pipeline.
- **Shadows (has a planned story).** CSM cast passes already have a per-cascade GPU-culler pool (Batch 221, WebGPUContextCullerPool.ts:15-16), so per-meshlet cull must run per-view (main + N cascades). The fork's own planned pattern FEAT-SURVEY-25 — "sharedSourceBuffer compute-cull fanout: one entity stream, many rendering variants: CSM cascades + TAA history + Hi-Z re-cull" (WEBGPU_MIGRATION_BACKLOG.md:274) — slots meshlets in directly.
- **Software rasterization breaks pick, depth interop, and classification simultaneously** (fragment pick path needs a visbuffer material resolve that 32-bit packing cannot carry; log-depth/hardware-depth interop with an atomic depth buffer is unpriced) — a second independent reason to exclude SW raster from v1.
- **RTE/precision (mandatory design constraint, not a breakage).** All rendering paths must use RTE — meshlet vertex-pulling stores tile-local f32 vertices + per-tile RTC/high-low center with camera-relative subtract in-shader. The point-cloud processor's precision rationale (tile-bounded content is f32-safe) transfers directly (WebGPUPointCloudLODProcessor.ts:30-44; Batch 350 globe RTC precedent).

## 5. Tiered proposal

All tiers: **WebGPU-only additive**, WebGL keeps the standard per-tile draw path. This has three shipped precedents with "documented no-op on WebGL" (COMPUTE_INSTANCE_COLLECTION, FLOW_FIELD, FFT_OCEAN — FeatureRendererKey.js:201-271), and compute-driven meshlet culling + indirect draws has no WebGL2 equivalent path in the fork, satisfying CLAUDE.md Principle 5's "architecturally impossible" clause — but it needs explicit maintainer ratification (§6). Default-off, byte-identical-off gate contract, matching every recent additive seed.

**Tier 1 — Per-meshlet cull + indirect draw collapse (no LOD change). Effort: M-L, ~4-8 orchestrator batches. VERDICT: worth it; the recommended v1.**
Meshletize Model-content tiles at load in a worker via the in-tree MeshoptClusterizer (no METIS, no simplifier, no DAG); store meshlet bounds (sphere + normal cone) per tile in Phase-8b-shaped pooled GPU buffers; compute pass does per-meshlet frustum + normal-cone cull (Hi-Z later, when FORK-41's consumer ungates) writing drawIndexedIndirect args consumed through the existing WebGPUDrawCommand.drawIndirectBuffer path, grouped by WebGPUModelPipelineCache key (alphaMode | doubleSided | materialDefines — the "homogeneous pipeline runs" indirect batching needs); hardware raster only; carry the meshopt vertex remap so feature-ID/pick/styling lookups stay correct; per-view fanout for CSM via FEAT-SURVEY-25. Meshlet cull runs strictly on the output of the existing geometricError/SSE tile traversal, so refine add/replace semantics are untouched. This is the direct triangle-mesh analog of the shipped point-cloud LOD processor, and it is exactly the Wihlidal-2016/Aaltonen-2015 tier that nanite-webgpu's author recommends building first. It also becomes the first real consumer that forces the Hi-Z Scene wiring and GPU_SORT_KEYS scaffolds to completion (Principle 7/9: finish what the scaffolding implies).
Shader path note: the ShaderDefine Uint32 register is EXHAUSTED (bits 0-30 occupied; DEFERRED_WORK.md:31), so a define-gated variant of the model shader is blocked on C11-149; the unblocked route is new standalone WGSL sources with new ShaderSourceIds (meshlet cull compute + meshlet vertex-pull render) — the seed must name this fork in the road. **[Orchestrator correction at landing, Batch 753: C11-149 LANDED at Batch 739 — the hi-word `ShaderDefineHi` registry exists with 31 free bits (first consumer `ENHANCED_OCEAN`, Batch 746), so a define-gated variant is NO LONGER blocked. The standalone-ShaderSourceId route remains the recommendation for the meshlet cull/vertex-pull shaders since they are new sources, not variants of the model shader; a hi-word bit is available if a model-shader variant is ever needed.]**
Verification per house rules: Playwright probe on a dense photogrammetry tileset measuring draw-call count, culled-meshlet %, pixel-diff vs the non-meshlet path, plus a per-feature pick probe (Batch 141 template).

**Tier 2 — Intra-tile cluster LOD (per-tile mini-DAG, runtime cluster cut). Effort: L-XL, multi-week. VERDICT: plausible follow-on, do not bundle into v1.**
MeshoptSimplifier (with vertex_lock/'LockBorder' — meshopt_simplifier.d.ts:3,20-31) + spatial grouping (buildMeshletsSpatial/Flex avoids METIS entirely) builds a per-tile DAG with nanite-webgpu's monotonic-error schema; the runtime cut test is a one-line compute addition to the Tier-1 cull pass. Unique costs in this fork: reconciling double-LOD with the CPU/f64 tile SSE refinement (the point-cloud precedent explicitly frames within-tile LOD as "complementary, NOT a replacement" — WebGPUPointCloudLODProcessor.ts:17-28), seam handling at group borders, eviction tied to tile unload, and meshoptimizer's own maintainer noting greedy clustering "sometimes missteps" vs METIS grouping (zeux discussion #750, experimental PR #760, no shipped DAG API). Cross-tile DAGs remain out of scope at any tier without non-standard offline content.

**Tier 3 — Nanite-complete (visibility buffer + compute SW raster + streaming DAG). Effort: XL, research-grade. VERDICT: NOT worth it for a globe engine on browser WebGPU today — say so plainly.**
The 64-bit-atomic gap forces either untextured output (nanite-webgpu's pack) or native-only extensions (Bevy's route, unavailable in browsers). Unpriced globe-engine couplings: log-depth interop, pick/pickPosition + depth-blit, CSM cast lists, TAA motion vectors, OIT/classification, multi-frustum execution, request-render economics, per-tile streaming lifetime — each a named audit surface under Principle 6 before this is defensible. The marginal win over Tier 1+2 is only sub-pixel raster efficiency, which the tile SSE traversal already bounds. Prior in-repo sizing agrees: "1-2 month spike... Not now" (archive/SESSION_2026-04-08_RESEARCH_REPORT.md:224). Revisit if/when WebGPU standardizes 64-bit atomics or drawIndirectCount.

**Named prereqs (all small, all pre-existing items):** (a) ADAPTIVE_LIMIT_CAPS entry for maxStorageBufferBindingSize (S); (b) FAR-003 culling re-arm story + FORK-41 Hi-Z consumer fix; (c) C11-168's dense-tileset measurement lane (W1-PARTIAL as of 2026-07-22, "representative content lanes open" — QUEUE_2026-07-18_CAMPAIGN11.md:494,851-854) is a hard prerequisite for *launching* (not seeding) a meshlet campaign — without it there is no baseline to prove any win; idle-soak FPS is invalid under request-render mode, the moving-altitude methodology is mandated; (d) device-loss/multi-context hygiene: all meshlet resources register onDeviceInvalidated and route through the shared compute/render pipeline caches (WebGPUContext.ts:5581-5649).
